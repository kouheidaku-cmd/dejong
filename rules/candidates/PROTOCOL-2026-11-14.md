# 事前登録: 現行ルールの見直し (v4 の仮の案) を、まだ見ていない 2005〜2018年で確かめる (2026-11-14)

このファイルと候補の仕様は、**検証を1回も走らせる前に**コミットする。
結果を見てから仕様や基準を変えた場合は、その事実と理由をレポートに必ず書く。

## きっかけ

人からの依頼 (2026-11-14): 「今の現行のプログラムも好きなように修整してみて。一回全部見直して。変更まで完了せずに仮で」。
合わせて、目標が変わっている: 「資産がとても上がること。4か月で 20% くらい。多少のリスクには目をつむる」(同日)。

これまでの検証を読み直すと、同じ形が4回続いている:

| 案 | リターン | 下落 | これまでの扱い |
|---|---|---|---|
| トレンド崩れで売らない (10/20 案1) | 大きく上がる | 同じか小さい | トレード数の基準で不採用 → v2 に一部として採用 |
| 弱い保有の入れ替え w1 (10/24) | 8年 +110% → +254% | 各年の平均 14.7% → 16.4% | 下落の基準で採用せず、フォワードテスト |
| 押し目買い d1 (11/10) | 12通りすべてで高い | 12通りすべてで約2ポイント大きい | 人の判断で見送り、フォワードテスト |
| ATR × 3 の損切り s2 (11/13) | 12通りすべてで高い | ほぼ同じ (5/12) | 人が決める → フォワードテスト |

どれも「リターンは上がるが、下落が少し増える」で止まっている。基準が下落に厳しかったためで、目標が変わったいまは、この引き換えを取る側に寄せてよい。
ただし問題は、**これらの案がすべて同じ8年 (2018-10〜2026) を見て選ばれている**こと。組み合わせて良く見えても、同じデータの見直しでしかない。

そこで、**これまでの21案が一度も使っていない 2005〜2018年**の日足を、初めて検証に使う。リーマンショック (2008年) を含む。

## 候補 (4つ。新しく作ったのは最後の1つだけ)

| 名前 | 中身 | ファイル |
|---|---|---|
| v3 | 現行 | `config/rules.yaml` |
| s2 | v3 + 損切り幅を ATR × 3 に | `rules/candidates/2026-11-13-s2-atr3.yaml` (既存) |
| w1 | v3 + 弱い保有と強い候補の入れ替え (60日リターンの差 20ポイント、28日以上保有) | `rules/candidates/2026-10-24-w1-swap-gap20.yaml` (既存) |
| **v4-draft** | v3 + s2 + w1 (2つを足しただけ。数字は既存の案のまま) | `rules/candidates/2026-11-14-v4-draft.yaml` (新規) |

- 新しい数字は1つも足していない。v4-draft は、それぞれ別々に「リターンは安定して上がる」と分かった2つの変更の組み合わせ
- 押し目買い d1 は入れない (対象の17銘柄が後から見て勝った銘柄で、古い期間では偏りがさらに大きくなるため)
- 利確 (+20% で半分) をやめる案は、今回は入れない (v1 のときに下落が増えて不採用。候補を増やしすぎない)

## 評価の方法

```bash
# A. まだ見ていない期間 (主な判定): 2005〜2018年10月
python -m trader phases config/rules.yaml rules/candidates/2026-11-13-s2-atr3.yaml rules/candidates/2026-10-24-w1-swap-gap20.yaml rules/candidates/2026-11-14-v4-draft.yaml --years 23 --until 2018-10-31 --name 2026-11-14-holdout-phases
# B. これまで使ってきた期間 (参考): 2018〜2026年
python -m trader phases config/rules.yaml rules/candidates/2026-11-13-s2-atr3.yaml rules/candidates/2026-10-24-w1-swap-gap20.yaml rules/candidates/2026-11-14-v4-draft.yaml --years 9 --name 2026-11-14-recent-phases
```

`--until` は今回足したオプション (yearly には前からある)。指定しなければ今までと同じ結果になる。

## 判定の基準 (`config/strategy.md` の「ルールの直し方」と同じ形。A で判定し、B は向きがそろうかを見る)

1. **v3 そのもの**: A で「同じ持ち高の指数」を上回る区切りが 10/12 以上あるか。
   なければ、「v3 は指数を薄めたものと変わらない」という 11/10 の結論が、別の13年でも確かめられたことになる
2. **各候補 対 v3** (A):
   - 12通り中10通り以上でリターンが高く、**かつ** 10通り以上で各年の最大下落の平均が大きくない → 採用候補
   - リターンは 10通り以上で高いが、下落は大きい → **人が決める**。そのとき「下落が平均で何ポイント増えるか」を示す。
     目標が変わったので、**増え方が3ポイント以内なら、v4 として勧める** (この線は結果を見る前にここで決めておく)
   - リターンが高いのが 10通り未満 → 勧めない。B で良く見えていたのは、同じ8年に合わせた結果だったと判断する
3. **各候補 対 同じ持ち高の指数** (A): 上回った区切りの数を、v3 と並べて報告する
4. A と B で向きが逆 (A では悪く、B では良い) の候補は、勧めない
5. トレード数が v3 の半分以上

どの結果になっても `config/rules.yaml` は書き換えない (今回は仮の案まで)。勧める案が出た場合も、フォワードテストに足すかどうか、実際の口座に使うかどうかは人が決める。

## 事前に分かっている弱点

- **後知恵の偏りは、古い期間ほど大きい。** 母集団は 2026年の大型株 61銘柄。2005年の時点でそれを選べたはずがない (NVDA・AAPL・AMZN など)。
  ルール同士の比較は同じ母集団なので成り立つが、指数との比較はルールに有利に出る。それでも指数に勝てなければ、結論は強い
- 2005年にはまだ上場していない銘柄がある (リクルート 2014、ソフトバンク 2018、META 2012、TSLA 2010 など)。上場後から対象になる
- 決算日のデータは Yahoo Finance で 2011年ごろより前がほとんど取れない。その期間は「決算前は買わない」が効かない (4候補とも同じ条件)
- 検証の買いシグナルは円換算の価格で計算している (日次はドル建て)。11/10 の点検の E。今回は直さずに走らせ、別に影響を測る
- 配当は入っていない (ルールも指数も)
- 12通りの区切りは互いに重なっていて、独立した12回ではない
- 私 (Claude) は surge を作るときに、別の仕組み (米国株の集中モメンタム) で 2005〜2018年の成績を見ている。v3 の系統のルールをこの期間で走らせるのは今回が初めて
