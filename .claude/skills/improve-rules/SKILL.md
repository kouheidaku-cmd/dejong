# 売買ルールの検証と改善

## 一番大事なこと: 過去に合わせすぎない
同じ過去データで「負けた → 直す」を繰り返すと、過去には完璧で将来には通用しないルールができる (過剰最適化)。
これを防ぐために次を必ず守る。

- 改善案は **学習期間 (前70%)** の結果だけを見て作る。検証期間を見てから案を作り直さない
- **検証期間 (後30%) はもう使い切っている** (2026-11-10 までに 21案を試し、20回以上見た)。検証期間の成績は参考にとどめ、
  採用の判定は下の「12通りの区切り」と、その後のフォワードテストで行う
- 案・対象・採用の基準は、検証を1回も走らせる前に `rules/candidates/PROTOCOL-<日付>.md` に書いてコミットする
- 数字の小さな差で決めない。8年のリターンで10ポイント、下落で2ポイント程度の差は、区切り方や偶然で出る (`reports/rules/2026-11-10-review.md`)
- 1回のセッションで試す改善案は **最大3つ**。1つの案で変えるのは **パラメータ1〜2個**
- 学習期間のトレード数が **30件未満** の比較は判断材料にしない
- 特定の1銘柄だけで成績が変わる案は採用しない
- `config/rules.yaml` を直接書き換えない。採用は人の了承を得てから

## 手順

1. **準備**
   ```bash
   git pull --ff-only
   pip install -q -r requirements.txt
   ```

2. **現行ルールのバックテスト**
   ```bash
   python -m trader backtest --years 8 --name <日付>-baseline
   ```
   画面には要点、`reports/backtest/<name>/` に全結果 (result.json, trades_*.csv, equity_*.csv) が出る。
   見る指標: 総リターン・最大ドローダウン・シャープレシオ・勝率・損益比 (profit_factor)・トレード数、
   ベンチマーク (母集団を均等に買って持ち続けた場合) との差。

3. **損失の分析 (学習期間だけ)** — `result.json` の `in_sample.analysis` と `trades_in_sample.csv` を読む:
   - `by_exit_reason`: どの売り理由で損しているか (例: 損切りが多すぎる → 入り方が悪い / 損切り幅が狭い)
   - `entry_features_losers_vs_winners`: 負けトレードと勝ちトレードで、買ったときの RSI・60日リターン・SMA20乖離に差があるか
   - `worst_trades` と `worst_tickers`: 大負けに共通点があるか (急騰後の買い、決算またぎ、特定の業種など)
   - 必要なら負けトレードの銘柄・時期を WebSearch で調べ、ルールで防げた損失か (防げない事故か) を見極める

4. **改善案を作る** — 分析から仮説を立て、`rules/candidates/<日付>-<短い名前>.yaml` に rules.yaml のコピーを作って変更する。
   例: 「損切りの7割が買って2週間以内 → 過熱気味で買っている → max_rsi 70→65」

5. **改善案のバックテスト**
   ```bash
   python -m trader backtest --years 8 --rules rules/candidates/<file>.yaml --name <日付>-<短い名前>
   ```

6. **採用の判定** (基準は `config/strategy.md` の「ルールの直し方」。2026-11-10 に作り直した)
   ```bash
   python -m trader phases config/rules.yaml rules/candidates/<file>.yaml --name <日付>-phases
   ```
   1年の区切りを1月〜12月始まりの12通りに変えて、現行ルール (最初のファイル) と「同じ持ち高の指数」
   (指数 50/50 をルールと同じだけ持ち、残りを現金にしたもの) と比べる。10分ほどかかる。
   - `vs_rules.return_higher` と `drawdown_not_larger` が**どちらも 10 以上** → 採用候補
   - 片方だけ (リターンは高いが下落も大きい、など) → 合否を付けず、差の大きさ (`avg_drawdown_diff` など) を示して人に決めてもらう
   - どちらも 10 未満 → 不採用
   - `beats_index_same_exposure` (同じ持ち高の指数を上回った区切りの数) も必ず報告する。現行ルールの値と並べる
   - トレード数が極端に減っていない (現行の半分以上)。別枠 (sleeves) は、一番稼いだ1銘柄を除いても損益がプラス
   - 採用候補は、フォワードテスト (`config/forward.yaml`) に足して3か月以上見てから、実際の口座に使うかを人が決める

7. **レポート** — `reports/rules/<日付>.md` に書く:
   - 現行ルールの成績 (学習・検証、ベンチマークとの比較)
   - 損失分析で分かったこと
   - 試した案ごとの仮説・変更点・成績の比較表・判定
   - 注意: 母集団が「今の大型株」なので過去の成績は生き残りバイアスで良く見えやすい
   - バックテストには実際の口座と同じドローダウン停止 (`settings.yaml` の risk) が入っている。`metrics.halt_days` が停止していた日数

8. **記録を残す**
   ```bash
   git add rules reports
   git commit -m "rules: <日付> の検証"
   git push
   ```

9. **人に了承をもらう** — 採用候補があれば、最後の返答で「何を・なぜ・どれだけ良くなったか」を短く示して了承を求める。
   了承されたら `config/rules.yaml` に反映して `version` を1つ上げ、`config/rules_changelog.md` に
   変更内容・理由・前後の成績を追記し、`config/strategy.md` の機械ルールの説明も合わせて直す (人の了承の範囲で)。
